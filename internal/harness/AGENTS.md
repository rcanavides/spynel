# Harness Adapter DOX

## Purpose

- Own the provider-neutral harness interface, catalog/factories, transactional supervisors and the unified multi-provider Runtime lifecycle, and Codex, Claude Code, Agent Zero CLI, Pi, and ACP process adapters.
- Keep role routing provider-neutral: callers select logical roles such as chat, developer, reviewer, notification, or heartbeat; concrete provider names remain confined to harness configuration and adapters.
- Keep provider retirement and structural replacement fail-closed and idle-only. ProviderID is the normalized provider instance identity from the RuntimeSpec topology key; HarnessConfig.Name remains the harness/catalog kind, so several provider instances may share one kind. Each provider instance ID owns at most one stable Supervisor and one exclusive session-file path; persisted session paths stay exclusive between provider instances, and matching roles share that Supervisor.

## Local Contracts

- `providerProcess` owns each provider OS process lifecycle: exactly one Wait owner publishes an immutable exit snapshot whose `requested` flag is true only when a Stop began before that Wait observed the exit, so a Stop after a natural exit can never reclassify it. Startups use `exec.Command` with an explicit `os.Pipe` stdout so buffered provider output stays readable after leader exit, Unix providers lead their own process group, and the Wait owner sweeps that group at natural exit so descendants cannot outlive their leader. Stop is one idempotent bounded escalation — cooperative stdin EOF, group TERM, group KILL, final group sweep — whose context cancels grace waiting but never cleanup, and only a genuinely expired kill grace may report a kill timeout; Stop failures surface through the closing adapter's error return (ACP, Codex) or configured stderr diagnostics (Pi, Claude) instead of being discarded. Adapter readers own stdout and close it exactly once after draining; Claude interruption stays an interrupt — group SIGINT on Unix, the Windows direct-process termination fallback — never the full stop escalation; and short-lived probe commands using `Run` may keep `exec.CommandContext`.
- Runtime is the sole production lifecycle owner for chat, developer, reviewer, notification, and heartbeat. RuntimeSpec contains providers and role mappings; RoleChat defines the primary and unspecified roles fall back to it. Validate normalized IDs, mapped providers, routed custom ACP configuration, and unique session-file ownership before construction/publication; custom ACP command validation keys on the harness kind, never on the instance identity, and one empty identity with an empty harness name remains the legacy no-harness-selected marker so harness-free service state stays constructible. Operational role targets remain stable and never expose provider lifecycle methods. No RoleSet or separate routed lifecycle exists.
- Runtime binds admitted session keys to their exact provider instance, retaining that instance ID and its Supervisor while reservations/admissions or logical work remain. Re-probe a zero-admission binding outside the mutex and revalidate its identity before reuse; stale idle bindings must resolve the current role, never resurrect a retired provider. `ReserveExecution` is role-based new admission; `ReserveOwnedExecution` constrains already-owned work to its exact nonempty `ProviderID` without role or chat fallback. Admission reservations span workflow claims, job attribution, and dispatch; durable orchestrator callers record a successful reservation's exact nonempty returned instance ID in `Lease.Provider` through their existing lease save. Durable orchestrator recovery resolves existing owned work through `ReserveOwnedExecution` on that exact recorded instance; only an empty legacy owner without a recorded instance uses role-based `ReserveExecution` and adopts its exact nonempty returned instance ID. Bound controls, interruption, activity, thread lookup, conversation admission, and resets retain the exact instance owner across role remaps; Runtime-backed identity always reports the bound or routed instance ID and never reconstructs it from `HarnessConfig.Name`, while injected non-Runtime targets keep the legacy harness-name fallback.
- Serialize Start, Close, and reconciliation using lifecycle reservations, never a mutex held over provider work. Reconciliation fences only affected providers, rejects retirement while bindings, logical turns, or operational lifecycle work remain, prepares structural changes through Supervisor.PrepareChange/Commit/Abort, and publishes role mappings atomically with each role's instance ID and Supervisor. Unchanged providers retain their Supervisor and process. Added providers start before publication; routed startup failure remains explicitly unavailable without chat fallback or shutdown of healthy providers, and later reconciliation retries the same Supervisor. Chat startup errors retain the server's existing unavailable-start behavior. Close retires each unique Supervisor once: it cancels the runtime-owned shutdown lifetime before waiting on any lifecycle reservation so a blocked Start or Reconcile unblocks, publishes the closed state exactly once with every concurrent or repeated caller sharing the one stored orchestration result, closes stop channels and joins every provider readiness watcher outside the mutex before supervisors close, and shuts independent supervisors concurrently with deterministic ProviderID error attribution and per-target panic containment. Reconcile runs provider startup and preparation under the caller context joined with that shutdown lifetime, publishes the new providers and roles before any retirement, then closes removed supervisors and replaced previous harnesses concurrently, joining each removed watcher before the supervisor close; a retirement failure after publication returns `errors.Join(ErrRetirementIncomplete, …)` with deterministic attribution while the published topology stays active and is never rolled back, and failures before publication abort prepared candidates and close newly added supervisors exactly once with cleanup errors joined after the primary cause. Whole-runtime shutdown never waits for active turns to complete naturally; adapter Close implementations stop their owned provider processes concurrently.
- Runtime.Start owns initial provider startup under one caller context joined with the runtime-owned shutdown lifetime. Production calls Start exactly once per process; repeated Start remains supported for tests and concurrent lifecycle exercise, where already-started providers are idempotent and a still-failed provider retries with one fresh bounded diagnostic per attempt. Start failure semantics stay per-role: the primary chat provider's error is returned unchanged, while a failed non-primary provider keeps Runtime.Start returning nil, stays explicitly unavailable for later reconciliation, and writes exactly one bounded diagnostic naming its ProviderID through the provider's already-wired `HarnessConfig().Stderr` with no new logging subsystem. A superseded joined lifetime must not simply be cancelled by a later Start because running supervisors may still derive from it; each stored AfterFunc registration self-releases when shutdown cancels, so repeated Starts cannot leak goroutines.
- Forward Supervisor broadcast Readiness into Runtime's close-and-replace broadcast, including topology changes; multiple observers independently recheck current state. This is wakeup forwarding, not another availability state machine. Never hold Runtime's mutex across Supervisor calls, provider I/O, emitters, or application persistence callbacks. Admission reservations provide exact `JobDetails.Provider` attribution and the sole provider-instance identity that durable orchestrator callers may persist; workflow Markdown and harness kind names never supply `Lease.Provider`.
- Keep application and orchestration code harness-neutral; adapters map native events into the common response and follow-up contract.
- Supervisor structural changes reject active logical executions and queued continuations unchanged, then fence new admissions and drain transient provider calls through their return before candidate construction. Preparation and draining honor the preparation context. Existing Send and SendConversation admissions wait through the structural fence with their caller context and use the adapter published by commit or retained by abort; Start also waits for settlement. Controls, discovery, inference/configuration changes, and session resets fail closed while fenced. Interrupt while fenced and idle returns false without provider I/O. Commit publishes only in-memory state and transfers the previous adapter to the caller for retirement outside locks; abort cleans up only the candidate before restoring admission. Before service startup, preparation remains configuration-only. Close waits for active preparation, then owns and cleans up any abandoned prepared candidate and the current adapter without requiring caller settlement. Abort after commit or Close is a safe no-op, and Commit after settlement publishes nothing. Lifecycle reservations span provider I/O without retaining the supervisor mutex, and inference persistence shares the dispatch barrier so callbacks may inspect state without changing snapshot ordering. Existing per-session send/control serialization remains intact. Lifecycle tests use fixture channels and testing/synctest quiescence to establish blocked operations without timing assumptions.
- `ErrProviderAbsent` means an owned reservation's exact instance ID is absent from the currently published Runtime topology. Keep it distinct from temporary structural fencing (`ErrProviderFenced`) and closed, start-failed, or otherwise unavailable providers (`ErrProviderUnavailable`, retaining the startup cause); pass admitted provider execution errors through unchanged. Owned admission never falls back through role or chat. Keep the legacy `ReadyEvents` edge for existing callers and expose versioned close-and-replace `Readiness` snapshots for independent observers; observers acquire a new snapshot after each wakeup, and readiness is a signal to recheck state, never proof of availability.
- Codex maps strictly boolean `error.willRetry: true` to nonterminal `reconnecting` status, retaining diagnostics in captured events. Only nonempty agent-message, reasoning, or plan deltas for the exact active turn restore `running`; tool output and generic activity do not establish upstream recovery. Missing/false/malformed retry flags remain errors. Serialize admission, deferred replay, live notifications, and transport failure through callback publication; publish admission first and reject another turn's late events. Transport failure also fences pending admission so a successful RPC reply cannot resurrect an exited provider.
- Resume Codex threads with `excludeTurns: true`: Codex retains its conversation context, while Spynel consumes only thread identity and its own bounded history. Any resume failure preserves the saved session and rejects dispatch instead of silently creating a replacement conversation. Keep the shared 16 MiB message bound; overflow and EOF close provider stdin as well as cancelling the subprocess so npm-launched native children receive EOF, fail pending/active work, and remain visibly unavailable through the supervisor until explicit restart or successful reconfiguration. Overflow diagnostics inspect only a bounded envelope prefix to identify a known notification or the correlated pending RPC, report unavailable metadata explicitly, and name the message-size limit and reconnect action without exposing payloads, provider IDs, arbitrary method strings, or replaying interrupted requests.
- Declare native-steer versus queued follow-up behavior explicitly, fence active executions, and invoke durable iteration reservation exactly once immediately before accepted provider delivery.
- Expose the provider-neutral new/steered/queued conversation admission classification at the same session fence so application correlation can cover consolidated terminal responses exactly.
- When an ordinary queued follow-up replaces an emitter, deliver its predecessor's continuing result followed by an explicit done-status release. This closes every request and balances application/channel activity without claiming logical completion. Orchestrator controls that preserve their emitter do not release it.
- An interruption attempt cancels not-yet-dispatched ordinary follow-ups with a terminal error per request, including every emitter in a dequeued batch. Capture the cancellation generation when removing queued work, preserve it through batching, and reject stale dispatch even if a successor turn is active. Queued controls retain their shared emitter; only the provider owns that execution's terminal event. Failure to interrupt the active provider does not restore already-cancelled queued requests.
- Order forward-looking model commits and dispatch snapshots under one supervisor fence. Never mutate an already-admitted provider turn; native steering remains part of that turn, while queued continuations and later top-level turns snapshot the newest model at their own provider-dispatch admission.
- Extend that fence to reasoning effort and service mode. Catalog metadata declares effort support for Codex, Claude, and Pi. Their model and effort values pass through to the provider without requiring discovery or catalog membership; validate bounded effort syntax at the shared boundary and let provider errors report unsupported manual choices. Codex reads per-model effort/service tiers for detected choices and passes `effort`/`serviceTier`; service selections still require verified capabilities. Claude passes `--effort`. Pi identifies its current/default model and current thinking level from `get_state`, queries each catalog model's exact RPC thinking levels in a separate no-session process selected by the non-persistent `--model` runtime override, labels a default effort only for the authoritative current model, and passes `--thinking`; never use Pi's persistent `set_model` RPC for capability inspection. Both legacy omitted and explicit Pi efforts reach the provider for validation/clamping. ACP model selection remains supported, but reasoning and speed are unsupported because ACP advertises optional thought choices only after session creation and defines no standard speed category.
- Build commands without shell interpolation, bound scanner/event payloads, surface startup and negotiation diagnostics, and keep portable fixture providers synthetic.
- Keep Agent Zero CLI as the fixed `agent-zero` profile backed by the shared ACP adapter, launch `a0 acp`, and require a bounded successful `a0 acp --check` before reporting it available.
- ACP v1 has no per-turn ID on `session/update` and no output-close marker after the prompt response. A successful turn is TERMINAL when its prompt result arrives and DRAINED after a bounded quiet window, hard cap, or transport/lifetime termination; emit Done only after DRAINED and keep `IsActive` true while draining. Any associated update resets the quiet window, while the hard cap remains measured from TERMINAL. Once TERMINAL success is recorded, later transport failure or Close cannot downgrade it to an error. Updates arriving after Done with no active turn are dropped rather than buffered for another turn.
